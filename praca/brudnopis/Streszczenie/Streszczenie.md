## Streszczenie

W pracy zaprojektowano i zaimplementowano prototyp platformy uczelnianej inspirowanej systemem USOS oraz forum PolWro, wykorzystującej grafową bazę danych Neo4j do przechowywania danych uczelni oraz modelowania kontroli dostępu RBAC i ReBAC. System obejmuje schemat oparty na typach grafu, wieloetykietowości i etykietach implikowanych, szyfrowane API w języku Python (FastAPI) z uwierzytelnianiem JWT oraz aplikację kliencką w Vue.js w środowisku Docker Compose. Aby ocenić przydatność podejścia grafowego, przygotowano równoległą implementację w bazie relacyjnej PostgreSQL i przeprowadzono testy funkcjonalne, bezpieczeństwa oraz wydajności.

Z przeprowadzonych prac wynika, że choć bazy grafowe ułatwiają konceptualizację gęsto powiązanych danych i zajmują mniej miejsca na dysku, ich ograniczenia utrudniają budowę systemów wymagających ścisłej struktury. Typy grafu nie zastępują w pełni ograniczeń relacyjnych, brak hierarchii etykiet utrudnia skalowanie uprawnień, a rozbudowane zapytania Cypher nie są wyraźnie wygodniejsze od złączeń SQL. W pomiarach porównawczych PostgreSQL osiągał krótsze czasy odpowiedzi (przy akceptowalnej wydajności zapytań punktowych w obu bazach) i egzekwował więcej reguł w samym schemacie. W konsekwencji model grafowy dobrze sprawdza się na etapie projektowania, lecz dla systemu produkcyjnego o rygorystycznych wymaganiach integralności właściwszym wyborem pozostaje baza relacyjna.

## Abstract

This thesis designs and implements a prototype university platform inspired by USOS and PolWro, using the Neo4j graph database to store academic data and model role- and relationship-based access control (RBAC and ReBAC). The prototype combines graph types, multi-labeling, and implied labels with a TLS-encrypted Python (FastAPI) API, JWT authentication, and a Vue.js client deployed via Docker Compose. To evaluate the graph approach in practice, the project adds a parallel PostgreSQL implementation and runs automated functional, security, and performance tests.

The findings show that while graph databases aid in conceptualizing richly connected domains and require less disk space, their current limitations hinder systems that demand strict schema integrity. Graph types cannot yet replace relational constraints, the lack of label hierarchies limits permission scalability, and complex Cypher queries offer no decisive ergonomics advantage over SQL joins. Benchmarks favor PostgreSQL in response time while both databases handle point queries well, with PostgreSQL enforcing far more rules directly in the schema. Consequently, graph modeling fits early design well, whereas a relational database remains the stronger foundation for a production platform.
